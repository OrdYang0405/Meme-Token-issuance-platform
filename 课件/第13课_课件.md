## 二、知识回顾（5 分钟）

**Q1：MemeToken 的 `_trySwapAndLiquify` 函数中，`_inSwap` 变量起到什么作用？它够安全吗？**

> 答案：`contracts/MemeToken.sol:214` 中的 `_inSwap` 是一个互斥锁，防止重入——在 `_trySwapAndLiquify` 执行期间阻止再次进入。但这是**手动实现的简易锁**，不如 OpenZeppelin 的 `ReentrancyGuard` 完善：
> - `_inSwap` 只在 `_trySwapAndLiquify` 内部使用（行203-228），不保护其他可能被重入的函数
> - 如果未来有人新增一个调用外部合约的函数并忘记加 `_inSwap` 检查，重入通道就打开了
> - `ReentrancyGuard` 是函数级别的，每个带 `nonReentrant` 修饰符的函数都受到独立保护

**Q2：MemeFactory 的 `createToken` 函数中，为什么创建代币后要调用 `newToken.transferOwnership(msg.sender)` 而不是 newToken 直接在构造函数中将 creator 设为 owner？**

> 答案：`contracts/MemeFactory.sol:87`。因为 `new MemeToken(...)` 的构造函数执行 `Ownable(msg.sender)`（`contracts/MemeToken.sol:100`），此时 `msg.sender` 是 MemeFactory 合约地址。如果不在创建后转移所有权，MemeToken 的 owner 将永久固定在 MemeFactory 上——创建者无法管理自己的代币。这是一个**所有权传递链路**的安全设计问题。

**Q3：MemeFairLaunch 在 `_processPurchase` 中达到硬顶时立即调用 `_finalize(true)`。如果 `_finalize` 中有外部调用，会有什么风险？**

> 答案：`contracts/MemeFairLaunch.sol:170-172`。`_processPurchase` → `_finalize(true)` 发生在购买流程中。当前版本的 `_finalize` 只设置状态变量和 emit 事件，没有外部调用——所以是安全的。但如果未来升级增加了外部调用（例如自动添加流动性），就会引入重入风险：攻击者可以在 `_finalize` 的回调中再次调用 `buyPublic`，而此时状态尚未完全更新。

**引入**：三问指向同一个结论——**安全不是"现在有没有漏洞"，而是"架构是否在原则上防止未来引入漏洞"**。本课将带你以审计师的视角逐行审查项目合约，发现真实的安全隐患并逐一修复。

## 三、智能合约安全方法论（15 分钟）

### 3.1 安全审计的核心原则

```
审计师视角 ≠ 开发者视角

开发者：这条路径能走通吗？         → "能" = 功能正确
审计师：还有别的路径能到达这里吗？  → "不能" = 安全

攻击者的三个武器：
1. 时间     —— 在你不注意的区块之间插入交易
2. 顺序     —— 控制函数调用的先后顺序
3. 组合     —— 将 N 个"安全"的函数组合成一个"致命"的攻击链
```

### 3.2 威胁建模：本项目的攻击面

```
                       ┌──────────────────┐
                       │   用户资金风险    │
                       │  FairLaunch ETH  │
                       │  Pair 中的 LP     │
                       └────────┬─────────┘
                                │
        ┌───────────────────────┼───────────────────────┐
        │                       │                       │
   ┌────┴────┐           ┌─────┴─────┐          ┌─────┴─────┐
   │ 经济攻击 │           │  权限攻击  │          │  时序攻击  │
   │ Sandwich│           │ owner 越权│          │ 抢跑提案  │
   │ 价格操纵 │           │ 私钥泄露  │          │ 冷却期绕过│
   └─────────┘           └───────────┘          └───────────┘
```

### 3.3 Solidity 0.8.20 的内置安全特性

| 特性 | 保护什么 | 本项目利用情况 |
|------|---------|--------------|
| 默认 checked math | 溢出/下溢 | 全合约受益——所有算术操作自动保护 |
| `require` / `revert` | 条件不满足回滚 | 所有函数入口校验 |
| `custom error` | Gas 高效的回滚信息 | OpenZeppelin 5.x 的 `OwnableUnauthorizedAccount` |
| `immutable` / `constant` | 不可变变量 | `MAX_TAX`、`TAX_COOLDOWN` 等使用 `constant` |

> **关键认知**：Solidity 0.8 的 checked math 消除了传统的整数溢出漏洞，但**逻辑漏洞**（如价格操纵、权限滥用、时序攻击）是编译器无法保护的——必须由开发者自己审计。

## 四、重入攻击：原理与防护（20 分钟）

### 4.1 经典重入攻击原理

```
攻击合约：
  1. buyPublic() 支付 1 ETH → 获得 tokensOwed
  2. 时间到期 → finalize()
  3. claimTokens() → token.transfer(attacker, tokens)
     └── token.transfer → 触发 ERC20._update
         └── 如果是 ERC777 风格，会回调 attacker 的 tokensReceived()
             → attacker 在回调中再次调用 claimTokens()
             → tokensClaimed[attacker] 还是 false（尚未更新！）
             → 再次获得全额代币
  4. 重复步骤 3，直到合约余额耗尽
```

**本项目中的实际风险**：

```solidity
// contracts/MemeFairLaunch.sol:203-213 — 当前代码

function claimTokens() external nonReentrant {
    require(launchSucceeded, "launch not successful");
    require(!tokensClaimed[msg.sender], "already claimed");  // ← 检查

    uint256 amount = tokensOwed[msg.sender];
    require(amount > 0, "nothing to claim");

    tokensClaimed[msg.sender] = true;  // ← 状态更新
    require(memeToken.transfer(msg.sender, amount), "transfer failed");  // ← 外部调用
    //                                                                     ⚠️ 外部调用在状态更新之后！

    emit TokensClaimed(msg.sender, amount);
}
```

**审计结论**：✅ 当前代码是**安全的**，因为：
1. `nonReentrant` 修饰符提供了第一层保护（OpenZeppelin ReentrancyGuard）
2. `tokensClaimed[msg.sender] = true` 在外部调用之前设置——符合"检查-生效-交互"（CEI）模式

**但有一个重要的"如果"**：如果忘记写 `nonReentrant`，且 MemeToken 升级为 ERC777 风格代币，这个函数就会变成重入漏洞。**防御深度原则**——即使 CEI 模式被违反，`nonReentrant` 仍能兜底。

### 4.2 本项目中 SwapAndLiquify 的重入分析

```solidity
// contracts/MemeToken.sol:203-228

function _trySwapAndLiquify() private {
    if (
        accumulatedForLiquidity >= swapThreshold &&
        swapAndLiquifyEnabled &&
        !_inSwap &&                              // ← 简易重入锁
        address(uniswapV2Router) != address(0)
    ) {
        uint256 half = accumulatedForLiquidity / 2;
        uint256 otherHalf = accumulatedForLiquidity - half;
        accumulatedForLiquidity = 0;             // ← 状态先更新（CEI 模式）

        _inSwap = true;                          // ← 加锁

        uint256 ethBefore = address(this).balance;
        _swapTokensForEth(half);                 // ← 外部调用 1：Router.swapExactTokensForETH
        uint256 ethReceived = address(this).balance - ethBefore;

        if (ethReceived > 0 && otherHalf > 0) {
            _addLiquidity(otherHalf, ethReceived);  // ← 外部调用 2：Router.addLiquidityETH
        }

        _inSwap = false;                         // ← 解锁

        emit SwapAndLiquify(half, ethReceived, otherHalf);
    }
}
```

**审计发现**：

| 检查项 | 状态 | 说明 |
|--------|------|------|
| CEI 模式 | ✅ | `accumulatedForLiquidity = 0` 在外部调用之前 |
| `_inSwap` 互斥锁 | ⚠️ | 手动实现，只保护 `_trySwapAndLiquify`，不保护其他路径 |
| Uniswap Router 是可信的 | ⚠️ | Router 地址由 owner 设置——恶意的 owner 可指向恶意 Router |
| `amountOutMin=0` | ❌ | `_swapTokensForEth` 行238-239：滑点 0 = 无条件接受任何输出 |

> **课堂提问**：`_swapTokensForEth` 中 `amountOutMin=0` 意味着什么？攻击者如何利用？
>
> **答案**：`uniswapV2Router.swapExactTokensForETHSupportingFeeOnTransferTokens(tokenAmount, 0, path, address(this), block.timestamp)` 中的 `0` 是 `amountOutMin`。它告诉 Router："只要换出 ETH，无论多少我都接受"。攻击者可以在 `_trySwapAndLiquify` 被触发时，在同一区块中先执行一笔大额 swap 来操纵代币价格，使 `_swapTokensForEth` 以极差的价格成交——这被称为 **Sandwich Attack**（三明治攻击）。

### 4.3 三明治攻击（Sandwich Attack）详解

```
时间轴（同一个区块内）：

1. 用户卖出 → 触发 _trySwapAndLiquify
2. [攻击者] 抢先（front-run）：在用户的 swap 之前，先买入大量代币，推高价格
3. [合约] _swapTokensForEth(half)：合约卖出 half 个代币换 ETH
4. [合约] _addLiquidity(otherHalf, ethReceived)：用剩余代币+ETH 添加流动性
5. [攻击者] 尾随（back-run）：在流动性添加后卖出代币，获利了结

攻击者利润 = 
  (步骤 2 的买入 + 步骤 3 的卖出推高价格) +
  (步骤 4 添加流动性进一步推高) +
  (步骤 5 高位卖出获利)

合约损失 = 步骤 3 中以低于市场价卖出代币的损失
```

**影响评估**：在我们的项目中，每次 `_trySwapAndLiquify` 卖出的代币量是 `accumulatedForLiquidity / 2`。如果累积量很小（如 1000 代币），三明治攻击的利润不足以覆盖 gas 成本。但如果累积到较大值（如 100000 代币），攻击就变得有利可图。

### 5.2 关键审计发现

**发现 1：swapThreshold 无上限**

```solidity
// contracts/MemeToken.sol:367-369
function setSwapThreshold(uint256 _threshold) external onlyOwner {
    swapThreshold = _threshold;
}
```

如果 owner 将 `swapThreshold` 设为 `type(uint256).max`，`accumulatedForLiquidity >= swapThreshold` 将永远为 false——SwapAndLiquify 永久失效。累积的流动性代币永远锁在合约中，无法自动转化。

**修复建议**：

```solidity
uint256 public constant MAX_SWAP_THRESHOLD = totalSupply / 100; // 不超过总供应量的 1%

function setSwapThreshold(uint256 _threshold) external onlyOwner {
    require(_threshold <= MAX_SWAP_THRESHOLD, "threshold too high");
    require(_threshold > 0, "zero threshold");
    swapThreshold = _threshold;
}
```

**发现 2：LiquidityLocker 的 owner 越权解锁**

```solidity
// contracts/LiquidityLocker.sol — unlock 函数

function unlock(uint256 _lockId) external {
    // ...
    require(
        msg.sender == record.beneficiary || msg.sender == owner(),  // ← owner 可解锁任何锁
        "not authorized"
    );
    // ...
}
```

这是第10课中讨论过的设计取舍——owner 作为兜底路径。但从安全审计角度看，这意味着：
- 如果 Locker 的 owner 是 EOA，私钥泄露 = 所有人的锁仓可被提前提取
- 唯一的解决方案：将 Locker 的 owner 设为 TimelockController（DAO 治理）

**发现 3：rescueETH 可在任何时候被 owner 调用**

```solidity
// contracts/MemeToken.sol:377-381
function rescueETH() external onlyOwner {
    uint256 amount = address(this).balance;
    payable(owner()).transfer(amount);
}
```

这意味着 owner 可以在任何时刻提取合约中所有 ETH——包括处于 SwapAndLiquify 流程中已卖出但尚未添加流动性的 ETH。如果 owner 在 `_swapTokensForEth` 之后、`_addLiquidity` 之前调用 `rescueETH`（通过抢跑），流动性添加将失败。

> **课堂提问**：`_inSwap` 标记能否阻止 owner 在 SwapAndLiquify 中途调用 `rescueETH`？
>
> **答案**：不能。`rescueETH` 不检查 `_inSwap`。`_inSwap` 只防止 `_trySwapAndLiquify` 重入自身——不阻止 owner 调用其他 `onlyOwner` 函数。这是一个**互斥锁作用域不足**的问题。

## 六、SwapAndLiquify 深度安全审计（15 分钟）

### 6.1 完整的攻击链路分析

```
攻击前提：owner 是恶意地址（或私钥泄露）

攻击步骤：
  1. owner 调用 setUniswapRouter(maliciousRouter)
     → 将 Router 指向攻击者控制的恶意合约
     → setUniswapRouter 没有时效锁！

  2. 等待 accumulatedForLiquidity 达到 swapThreshold

  3. 用户正常交易触发 _trySwapAndLiquify
     → _swapTokensForEth(half) 调用 maliciousRouter
     → maliciousRouter 收到代币但不返回 ETH

  4. ethReceived = 0
     → _addLiquidity 被跳过（ethReceived > 0 条件不满足）
     → 合约的一半累积代币丢失

  5. owner 调用 rescueETH() + rescueToken()
     → 将合约中剩余资产全部转走

最终结果：用户持仓的流动性被恶意 Router 劫持 + owner 卷走剩余资产
```

### 6.2 修复方案

**方案 1：Router 地址锁定**

```solidity
// 在启用交易后锁定 Router 地址
bool public routerLocked;

function lockRouter() external onlyOwner {
    require(!routerLocked, "already locked");
    require(address(uniswapV2Router) != address(0), "router not set");
    routerLocked = true;
}

function setUniswapRouter(address _router) external onlyOwner {
    require(!routerLocked, "router locked");  // ← 添加锁定检查
    require(_router != address(0), "zero router");
    uniswapV2Router = IUniswapV2Router02(_router);
    emit UniswapRouterSet(_router);
}
```

**方案 2：添加最小滑点保护**

```solidity
uint256 public constant MIN_SLIPPAGE_BPS = 50; // 0.5%

function _swapTokensForEth(uint256 tokenAmount) private {
    // ...现有路径代码...

    // 基于 Pair 储备计算最小输出量
    uint256 expectedOut = getExpectedOutput(tokenAmount); // 根据当前 reserves 计算
    uint256 minOut = (expectedOut * (10000 - MIN_SLIPPAGE_BPS)) / 10000;

    uniswapV2Router.swapExactTokensForETHSupportingFeeOnTransferTokens(
        tokenAmount,
        minOut,  // ← 不再是 0！
        path,
        address(this),
        block.timestamp
    );
}
```

### 6.3 安全等级评估

| 风险 | 严重程度 | 利用难度 | 影响范围 | 修复优先级 |
|------|---------|---------|---------|-----------|
| Router 可被指向恶意地址 | 🔴 严重 | 低（owner 权限） | 所有 SwapAndLiquify 中的代币 | P0 |
| `amountOutMin=0` 无滑点保护 | 🟡 中等 | 中（需 MEV 能力） | 单次 Swap 的代币量 | P1 |
| `_inSwap` 锁作用域不足 | 🟢 低 | 低（owner 权限） | rescueETH 竞争 | P2 |
| `swapThreshold` 无上限 | 🟢 低 | 低（owner 权限） | 累积代币永远不转化 | P3 |

### 7.2 DoS 攻击：LiquidityLocker 的无界循环

```solidity
// contracts/LiquidityLocker.sol — 查询函数

function getLocksByToken(address _token) external view returns (uint256[] memory) {
    uint256 count = 0;
    for (uint256 i = 0; i < locks.length; i++) {  // ← 遍历全数组
        if (locks[i].token == _token) count++;
    }
    // ...第二次遍历全数组...
    for (uint256 i = 0; i < locks.length; i++) {  // ← 再次遍历
        if (locks[i].token == _token) result[index] = i;
    }
    return result;
}
```

如果 `locks` 数组有 10,000 条记录，这个函数需要遍历 20,000 次。虽然在 `view` 函数中不会消耗实际 gas（仅在 eth_call 时执行），但在前端查询或合约间调用时会：
1. 前端请求超时（RPC 提供者的 gas limit）
2. 其他合约调用此函数时 `eth_call` 失败

**修复方案**：使用 EnumerableSet 或维护 `token → lockIds[]` 索引映射。

### 7.3 Merkle 证明的潜在问题

```solidity
// contracts/MemeFairLaunch.sol:123-141

function buyWhitelist(uint256 _ethAmount, bytes32[] calldata _merkleProof) external {
    require(!whitelistClaimed[msg.sender], "already claimed");
    bytes32 leaf = keccak256(abi.encodePacked(msg.sender));
    require(_merkleProof.verify(merkleRoot, leaf), "invalid proof");
    // ...
}
```

**潜在的"second preimage"问题**：`abi.encodePacked` 对动态类型不防碰撞。但由于 `msg.sender` 是 `address`（固定 20 字节），且 `keccak256` 的抗碰撞性，在实际中不会被利用。

**更安全的写法**：使用 `keccak256(abi.encode(msg.sender))` 替代 `keccak256(abi.encodePacked(msg.sender))`，消除任何理论上的哈希碰撞可能。

### 7.4 时间戳依赖与 15 秒规则

以太坊区块时间戳允许矿工在 ~15 秒范围内操纵。本项目中使用 `block.timestamp` 的场景：

| 位置 | 用法 | 风险 |
|------|------|------|
| `MemeToken.sol:291` | `TAX_COOLDOWN = 1 days` | 矿工最多操纵 15 秒，对 1 天来说可忽略 |
| `MemeFairLaunch.sol:112-115` | 阶段时间边界 | `whitelistEnd` 的精确边界可能被操纵 ±15 秒 |
| `LiquidityLocker.sol` | 解锁时间 | 对以天为单位的锁仓影响极小 |

**结论**：本项目不使用 `block.timestamp` 作为随机源或精确计时，所有时间依赖的操纵空间（±15秒）远小于业务时间粒度（1天），属于**可接受的风险**。

## 十、总结（5 分钟）

| 知识点 | 关键内容 | 受影响合约 |
|--------|---------|-----------|
| 重入攻击 | CEI 模式 + ReentrancyGuard 双层防护 | MemeFairLaunch, MemeToken |
| 三明治攻击 | `amountOutMin=0` 导致的价格操纵风险 | MemeToken._swapTokensForEth |
| 访问控制 | owner 权限过大 = 单点故障 | MemeToken(13个), Locker(owner解锁) |
| 恶意 Router | 无锁定机制，Router 可随时替换 | MemeToken.setUniswapRouter |
| 无滑点保护 | 两个 `amountOutMin=0` 调用点 | MemeToken._swapTokensForEth, _addLiquidity |
| DoS 攻击 | 无界数组遍历的 Gas 耗尽 | LiquidityLocker 查询函数 |
| 时间戳操纵 | ±15秒 不影响以天为单位的业务逻辑 | MemeToken, FairLaunch |
| Slither | 自动化检测 80+ 漏洞模式 | 项目整体 |
| CEI 模式 | Checks-Effects-Interactions 顺序 | 所有外部调用函数 |
| 防御深度 | 多层防护——任何单层失败都不导致漏洞 | 架构原则 |

**审计不等于"找 bug"**。审计的一等公民是**约束未来开发者不引入漏洞**——通过 API 设计（如 `lockRouter`）、编译器检查（checked math）、和自动化工具（Slither）建立多层防线。
